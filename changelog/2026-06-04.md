# Changelog — 2026-06-04

## Backend Critical Fixes — SF-004, SF-005, SF-002, PERF-002

Resolved all four Phase 1 critical backend issues. PR #69.

### SF-004 (CRITICAL) — Deleted `sendCommand` Error-Swallowing Wrapper (`backend/src/lambdas/expenses/index.ts`)
- **Gap**: A `sendCommand` helper wrapped every DynamoDB call in a silent `try/catch` that returned `undefined` on any exception. Throttling errors, IAM denials, and network failures all surfaced as 404 "Expense not found" instead of propagating the real error.
- Deleted the `sendCommand` function entirely.
- Replaced all three call sites with direct `ddb.send()` calls so exceptions propagate to `withErrorHandler` and the Lambda runtime, surfacing the correct HTTP status and error message.

### SF-005 (CRITICAL) — DELETE Authorization Failure No Longer Masked as Success (`backend/src/lambdas/expenses/index.ts`)
- **Gap**: `DELETE /expenses/{id}` caught `ConditionalCheckFailedException` and returned `200 { deleted: true, note: "not found or wrong owner" }` — an authorization failure (wrong owner) was indistinguishable from a successful delete.
- Added `ReturnValuesOnConditionCheckFailure: "ALL_OLD"` to the `DeleteCommand` so the exception carries the item back if it existed.
- In the catch block: `e.Item` present → `403 "Not authorized to delete this expense"`; `e.Item` absent → `404 "Expense not found"`.
- Updated `expenses.group-support.unit.test.ts` to assert the correct 403/404 responses instead of the previous 200.

### SF-002 (CRITICAL) — Textract Failure Writes Terminal Status to Scan Record (`backend/src/lambdas/receipts/index.ts`)
- **Gap**: `StartExpenseAnalysisCommand` was wrapped in `try/finally` only. On any Textract failure the scan record was left permanently stuck in `"processing"`, with no way for the frontend or operators to distinguish an in-flight job from a dead one.
- Converted `try/finally` to `try/catch/finally`: the catch block writes `status: "failed"` to the DynamoDB scan record via `UpdateCommand` before re-throwing.
- The `finally` block continues to close the X-Ray subsegment regardless of outcome.
- Added `UpdateCommand` to the `@aws-sdk/lib-dynamodb` import.

### PERF-002 (CRITICAL) — Removed O(N) Scan Fallbacks from GET and PATCH (`backend/src/lambdas/expenses/index.ts`)
- **Gap**: Both `GET /expenses/{id}` and `PATCH /expenses/{id}` fell back to a `ScanCommand` with `FilterExpression` when the direct key lookup missed. A full-table scan on every cache miss caused unbounded latency, unnecessary read-capacity consumption, and throttling errors that surfaced as false 404s.
- `GET /expenses/{id}`: removed the scan fallback; returns 404 immediately when `GetCommand` misses.
- `PATCH /expenses/{id}`: replaced the `QueryCommand` + scan fallback lookup with a single `GetCommand`. The partition key is derived from `groupId` (body or query param, for group expenses) or `USER#userId` (personal expenses) — always a targeted key read.
- Updated `expenses.unit.test.ts` PATCH `beforeEach` to mock `GetCommand` (was `QueryCommand`).
- Updated `expenses.group-support.unit.test.ts` scan-fallback tests to assert single-call 404 behaviour.

## Infrastructure Fix — IaC-007: ElastiCache Multi-AZ Cluster Count

Fixed a critical CloudFormation validation error that would abort every production deploy mid-stack. PR #68.

### IaC-007 (CRITICAL) — `numCacheClusters` must be ≥ 2 when `automaticFailoverEnabled` (`infrastructure/stacks/CostsCrunchStack.ts`)

- **Gap**: `numCacheClusters: 1` was set unconditionally while `automaticFailoverEnabled: isProd` evaluates to `true` in production. CloudFormation rejects this combination with `InvalidParameterCombination: fewer than 2 cache nodes required for multi-AZ`. The first prod deploy would have aborted at the `Redis` resource, leaving the stack in a failed state.
- **Fix**: Changed to `numCacheClusters: isProd ? 2 : 1`. Prod now provisions 2 cache nodes to satisfy the multi-AZ constraint; dev and staging keep 1 node (no cost increase).
- **Test gate**: `cd infrastructure && npm run synth` passes cleanly (exit 0).

## CI/CD Critical Fixes — BUG-002, BUG-003

Resolved the two remaining Phase 1 CI/CD critical issues in `rollback.yml` and `deploy.yml`. PR #70.

### BUG-002 (CRITICAL) — Health-Check `exit 1` Prevented Rollback and Notifications from Running (`rollback.yml`)
- **Gap**: The health check step called `exit 1` on failure, which put the step (and potentially subsequent logic) into a failed state before the rollback and Slack notification steps could execute. While `if: always()` was already on the rollback step, the premature `exit 1` meant the job never reached a clean terminal state after rollback completed — if rollback succeeded, the job would still show as failed at the wrong step rather than at the explicit terminal gate.
- Removed `exit 1` from the health check step (the `passed=false` output is written immediately before, so condition checks on subsequent steps are unaffected).
- Added a dedicated `Fail job if health check failed` step at the end of the job with `if: always() && steps.health_check.outputs.passed == 'false'`. The job now fails only after rollback and notifications have run, making the failure signal accurate and actionable.

### BUG-003 (CRITICAL) — Manual Dispatch Rollback Job Was a No-Op Stub (`deploy.yml`)
- **Gap**: The `rollback` job triggered by `workflow_dispatch` contained only `echo "Rolling back to previous stack version..."` with a `# implement with actual commands` comment. Operators triggering it during a production incident would receive a green checkmark and no rollback.
- Implemented the rollback job body:
  - `aws cloudformation rollback-stack --stack-name costscrunch-prod` — initiates the CloudFormation rollback to the previous deployed template.
  - `aws cloudformation wait stack-rollback-complete --stack-name costscrunch-prod` — blocks until the rollback is fully complete before the job exits.
  - Added a Slack notification step (`8398a7/action-slack`, same pinned SHA as elsewhere in the file) with `if: always()` — fires on both success and failure so operators know the outcome either way.

## Backend Safety Fixes — SF-006, SF-007, SF-008, SF-009, SIMP-001, SIMP-002, OPS-001, DEP-003

Resolved all eight Phase 2 backend-safety issues across WebSocket lifecycle, duplicate detection observability, auth guards, structured logging, and env var startup checks.

### SF-009 (IMPORTANT) — Duplicate Scan Records No Longer Stuck in "processing" (`backend/src/lambdas/sns-webhook/index.ts`)

- **Gap**: When a receipt was flagged as a duplicate, the pipeline emitted a `DuplicateDetected` event and hit `continue` without writing a terminal status. The scan record remained in `"processing"` indefinitely with no way for the frontend or operators to distinguish an in-flight scan from a detected duplicate.
- Added `writeScanDuplicate(expenseId, scanId)` helper (mirrors `writeScanFailed`) that writes `status: "duplicate"` via `UpdateCommand`.
- Called before the `continue` so the scan record always reaches a terminal state.

### SF-008 (IMPORTANT) — Duplicate Detection Bypass Is Now Observable (`backend/src/lambdas/sns-webhook/index.ts`)

- **Gap**: `ResourceNotFoundException` in `checkForDuplicate` silently returned `{ isDuplicate: false }` with only a log message. Both "GSI missing" and "table misconfigured" produced the same bypass with no CloudWatch signal.
- Added `metrics.addMetric("DuplicateCheckSkipped", MetricUnit.Count, 1)` to the catch block so every bypass is visible as a custom metric.
- Updated the `logger.warn` message to `"DuplicateCheckSkipped"` for consistent log querying.

### SF-007 (IMPORTANT) — Partial WebSocket Fan-Out Failures Are Now Observable (`backend/src/lambdas/web-socket-notifier/index.ts`)

- **Gap**: `Promise.allSettled` only re-threw when **all** connections failed. Partial failures (e.g. 1 of 10 users not notified) were absorbed silently — no metric, no log escalation.
- Added `metrics.addMetric("WsPartialFailures", MetricUnit.Count, errors)` in both `handleReceiptScanCompleted` and `handleQuarantineEvent` when `errors > 0`, making partial outages visible in CloudWatch dashboards and alarms.

### SF-006 (IMPORTANT) — WebSocket `$disconnect` Now Deletes Connection Record (`backend/src/lambdas/web-socket-handler/index.ts`)

- **Gap**: The `$disconnect` handler logged and returned 200 without touching DynamoDB. Stale connection records accumulated indefinitely and wasted WebSocket fan-out budget on every subsequent `pushToConnection` call.
- Added a `ScanCommand` (filtered on `connectionId` attribute) to locate the connection record, followed by a `DeleteCommand` to remove it.
- Note: a GSI on `connectionId` (infra-agent IaC coordination) should replace the scan for O(1) lookup at production scale; the current implementation is correct but linear.

### SIMP-001 (IMPORTANT) — `userId` Override Now Gated on `MOCK_AUTH` (`backend/src/lambdas/expenses/index.ts`, `backend/src/lambdas/expense-export/index.ts`)

- **Gap**: Hardcoded `userId` overrides (`"local-user-uuid-123"` → `"test-user-001"`) executed unconditionally in all environments — including staging and production — substituting a test identity for any request whose JWT returned the placeholder value.
- Wrapped both overrides in `if (process.env.MOCK_AUTH === 'true')` so they are only active in local dev environments where `MOCK_AUTH=true` is set explicitly.

### SIMP-002 (IMPORTANT) — `console.log` Calls Replaced with Structured Logger in Groups Handler (`backend/src/lambdas/groups/index.ts`)

- **Gap**: Five `console.log` calls in `normalizeRoute` and `rawHandler` fired on every request, bypassing `@aws-lambda-powertools/logger` and producing unstructured CloudWatch noise with no correlation IDs, severity levels, or JSON structure.
- Replaced all five with `logger.debug(message, { ...structuredArgs })` calls.
- Removed a redundant `DEBUG_LOGS`-gated duplicate that was shadowing the structured log immediately above it.

### OPS-001 (IMPORTANT) — Balances Debug Log Now Uses Structured Logger (`backend/src/lambdas/groups/index.ts`)

- **Gap**: `console.log("[DEBUG] Balances count: ...")` in the `GET /groups/{id}/balances` handler emitted an unstructured string to CloudWatch on every balances request.
- Replaced with `logger.debug("Balances calculated", { balancesCount: Object.keys(balances).length, settlementsCount: settlements.length })` so the metric values are queryable via CloudWatch Logs Insights.

### DEP-003 (IMPORTANT) — Startup Warning When `WEBSOCKET_ENDPOINT` Is Missing (`backend/src/lambdas/image-preprocess/index.ts`)

- **Gap**: `imagePreprocessLambda` read `process.env.WEBSOCKET_ENDPOINT || ""` and silently skipped quarantine push notifications when the string was empty, with no log or metric to indicate the env var was absent.
- Added a module-level `logger.warn(...)` block that fires at cold start when `WEBSOCKET_ENDPOINT` is falsy, making the misconfiguration immediately visible in CloudWatch.
- Note: the CDK injection fix (IaC-011, infra-agent) must merge before quarantine notifications function in deployed environments; this fix adds observability for the missing variable.

## Backend Performance & Scalability Fixes — CON-003, CON-004, PERF-003, PERF-004, SCALE-001, SCALE-002, SCALE-003

Resolved all seven Phase 2 backend-perf issues. PR #72.

### CON-003 (IMPORTANT) — `ApiGatewayManagementApiClient` Hoisted to Module Scope (`backend/src/lambdas/image-preprocess/index.ts`)

- **Gap**: `ApiGatewayManagementApiClient` was constructed inside `notifyUserViaWebSocket()` on every call. Because S3 events batch multiple records, each quarantine notification triggered a full TLS handshake and credential resolution cycle.
- Hoisted the client to module scope (matching the pattern in `web-socket-notifier/index.ts`). The endpoint guard now checks the module-level `wsClient` null reference instead of re-evaluating `WEBSOCKET_ENDPOINT` inside the function.

### CON-004 (IMPORTANT) — Shared `pushToUsers` Helper Eliminates Duplicated Fan-Out Logic (`backend/src/lambdas/web-socket-notifier/index.ts`)

- **Gap**: `handleReceiptScanCompleted` and `handleQuarantineEvent` contained identical 20-line `Promise.allSettled` fan-out blocks. Any bug fix had to be applied in two places.
- Extracted `pushToUsers(userId, connectionIds, payload)` helper that owns the allSettled loop, error tallying, and all-connections-failed throw. Both handlers call it and destructure `{ sent, stale, errors }`, then add their own domain-specific metrics.
- During rebase, the SF-007 `WsPartialFailures` metric (from backend-safety) was integrated into both handlers using the returned `errors` count.

### PERF-003 (IMPORTANT) — Category RegExp Patterns Precompiled at Module Init (`backend/src/lambdas/sns-webhook/index.ts`)

- **Gap**: `guessCategory()` called `new RegExp(...)` per keyword per category on every invocation — approximately 210 regex compilations per call against a static keyword list that never changes.
- Added `categoryPatterns` (an `Object.fromEntries` map from category name to a single combined `RegExp`) immediately after `CATEGORY_KEYWORDS`. The runtime loop now does a single `.test()` per category instead of N keyword compilations.

### PERF-004 (IMPORTANT) — JPEG Auto-Orient Without Re-Encode (`backend/src/lambdas/image-preprocess/index.ts`)

- **Gap**: The JPEG branch used `sharp().jpeg({ quality: 100 })` which, despite the comment "lossless quality", still re-encodes the image and introduces generation loss. Re-compressed JPEGs degrade Textract OCR accuracy on subsequent runs.
- JPEG branch now uses `sharp(buffer).withMetadata().rotate().toBuffer()` — EXIF-based auto-orient with no re-encode. PNG (lossless compression) and HEIC (format conversion) branches are unchanged.
- Updated `image-preprocess.unit.test.ts` to add `withMetadata` and `rotate` to the Sharp mock and assert the orient-only path.

### SCALE-001 (IMPORTANT) — Reimbursed Expenses Excluded from Balances Query (`backend/src/lambdas/groups/index.ts`)

- **Gap**: `GET /groups/{id}/balances` loaded the entire expense history for a group with `begins_with(sk, "EXPENSE#")` and no status filter. Groups with large expense histories would exhaust Lambda memory.
- Added `FilterExpression: "#status <> :reimbursed"` with `ExpressionAttributeNames: { "#status": "status" }` to avoid the DynamoDB reserved-word conflict. Only unsettled expenses are loaded; balance and settlement calculations are unaffected.

### SCALE-002 (IMPORTANT) — Group Analytics Fetched via `BatchGetCommand` (`backend/src/logic/analyticsRepository.ts`)

- **Gap**: `scope=all` analytics issued one `QueryCommand` for group memberships and then one `queryPartition` call (potentially paginated) per group — 21+ DynamoDB requests for a user in 20 groups per analytics page load.
- Replaced the N concurrent `queryPartition` group calls with a single `BatchGetCommand` keyed at `pk=GROUP#<gid>, sk=ANALYTICS#<startDate>:<endDate>`. Includes a standard unprocessed-key retry loop (100-item batches). Personal expenses are still fetched via `queryPartition`.
- Updated `analytics-repo.unit.test.ts` to mock `BatchGetCommand` and use the module-level table name constant for the `Responses` key.

### SCALE-003 ⚠️ Schema Change (IMPORTANT) — Active/Inactive Group Memberships Encoded in SK Prefix (`backend/src/lambdas/groups/index.ts`, `backend/src/logic/analyticsRepository.ts`)

- **Gap**: `GET /groups` used `begins_with(sk, "GROUP_MEMBER#")` with `FilterExpression: "active <> :false"`. DynamoDB charges read capacity for all scanned items before filtering — including inactive memberships.
- **⚠️ Data migration required** before deploying to any environment with existing data. Existing `GROUP_MEMBER#` items will not match the new `ACTIVE_GROUP_MEMBER#` prefix and users will appear to have no groups until migrated.
- Changed SK prefix to `ACTIVE_GROUP_MEMBER#` for active memberships; `FilterExpression` removed from `GET /groups`. All write paths updated: `POST /groups` (owner), `POST /groups/{id}/join` (member), `DELETE /groups/{id}` (now deletes the `ACTIVE_GROUP_MEMBER#` item rather than setting `active = false`).
- `analyticsRepository.ts` membership prefix updated to `ACTIVE_GROUP_MEMBER#` to match.

## Type Safety — TDA-001 TDA-002 TDA-003 TDA-004 TDA-005

Closed 5 compile-time type-safety gaps across shared backend utilities. Branch `feat/p2/types`.

### TDA-001 — ExpenseStatus Zod/TypeScript sync (`shared/validation/schemas.ts`, `shared/models/types.ts`)
- **Gap**: `expenseStatusSchema` accepted `"pending"` but the `ExpenseStatus` TypeScript type did not include it — schema and type were out of sync.
- Made Zod the source of truth: renamed to `ExpenseStatusSchema`, exported `type ExpenseStatus = z.infer<typeof ExpenseStatusSchema>`. Removed the duplicate union definition from `types.ts`; it now re-exports from `schemas.ts`. All downstream imports unchanged.

### TDA-004 — CategoryName enum enforced at API boundary (`shared/validation/schemas.ts`)
- **Gap**: `createExpenseSchema.category` used `z.string().max(50)` — any arbitrary string could reach DynamoDB.
- Added `CategoryNameSchema = z.enum(['Groceries','Travel','Software','Meals','Office','Equipment','Other'])` matching the existing `CategoryName` union in `types.ts`. Applied to both `createExpenseSchema` and `updateExpenseSchema`. Test fixtures updated to valid enum values.

### TDA-002 — withErrorHandler generic over event type (`utils/withErrorHandler.ts`)
- **Gap**: The `AnyHandler` base type used `event: any`, disabling compile-time event-type checking for every Lambda handler wrapped by `withErrorHandler`.
- Removed `AnyHandler`. Replaced with `<E, R>` generics: `withErrorHandler = <E, R>(handler: (event: E, context: Context) => Promise<R>) => ...`. Handlers with explicit event-type annotations now get full compile-time checking. `web-socket-notifier` still passes `event: any` inline and is noted for follow-up.

### TDA-003 — analyticsRepository.getExpenses typed as Promise<Expense[]> (`logic/analyticsRepository.ts`, `shared/validation/schemas.ts`)
- **Gap**: `getExpenses` returned implicit `any[]`; all downstream analytics pipeline field access was untyped.
- Added `ExpenseSchema` (Zod object with `.passthrough()`) to `schemas.ts`. Changed `getExpenses` and `queryPartition` return types to `Promise<Expense[]>`. Items are validated at the DynamoDB boundary with `ExpenseSchema.parse()`. `category` field in `ExpenseSchema` uses `z.string()` (permissive for DynamoDB reads/legacy data) while `CategoryNameSchema` enforces the enum for API inputs (TDA-004). Test fixtures updated to include all required Expense fields.

### TDA-005 — withAuth return type union (`shared/auth/middleware.ts`)
- **Gap**: The error branch returned `{ statusCode: 401 } as unknown as TResult` — a type lie. Callers could not detect the substitution at compile time.
- Changed return type to `Promise<TResult | APIGatewayProxyResult>`. Added `AuthorizedEvent` type for the enriched-event shape post-verification. Removed the `as unknown` cast; the 401 response now types correctly as `APIGatewayProxyResult`. No callers use `withAuth` directly (project uses the `withLocalAuth` + `getAuth` pattern).

## Infrastructure Phase 2 Fixes — IaC-008 through IaC-018

Phase 2 infrastructure hardening covering Lambda config, monitoring, correctness, and context-key fixes across `CostsCrunchStack.ts`, `GitHubActionsStack.ts`, and deploy scripts. Branch `feat/p2/infra`.

### IaC-014 (IMPORTANT) — authTriggerLambda read+write access (`infrastructure/stacks/CostsCrunchStack.ts`)
- **Gap**: `grantWriteData` only; `GetItem`/`Query` calls during post-confirmation profile creation hit `AccessDeniedException` because the auth trigger reads the user record before writing.
- Fix: `table.grantReadWriteData(authTriggerLambda)`

### IaC-015 (IMPORTANT) — BEDROCK_REGION env var (`infrastructure/stacks/CostsCrunchStack.ts`)
- **Gap**: Bedrock client in `sns-webhook` hardcoded `us-east-1`; cross-region deploys would route Bedrock calls to the wrong endpoint and fail silently.
- Fix: added `BEDROCK_REGION: regionId` to `sharedEnv`; lambda should read `process.env.BEDROCK_REGION ?? process.env.AWS_REGION` when constructing the `BedrockRuntimeClient`.

### IaC-016 (IMPORTANT) — Remove duplicate ManageConnections policy (`infrastructure/stacks/CostsCrunchStack.ts`)
- **Gap**: `execute-api:ManageConnections` policy added twice to `wsNotifierLambda` (exact duplicate block); CDK would emit a duplicate statement ID warning and the policy was unnecessarily verbose.
- Fix: removed the second `addToPolicy` block.

### IaC-012 (IMPORTANT) — CDK context key mismatch (`package.json`, `infrastructure/package.json`, `infrastructure/bin/`)
- **Gap**: All deploy scripts passed `--context env=<stage>` but `bin/costscrunch.ts` read `tryGetContext("stage")`; every deploy silently fell back to dev config regardless of the intended stage. A dead `bin/app.ts` entry point (using the old `env` key) was still referenced in the CDK `app` field.
- Fix: standardised all npm scripts in both `package.json` files to `--context stage=<env>`; updated the CDK `app` entry in `infrastructure/package.json` to `bin/costscrunch.ts`; deleted `bin/app.ts`.

### IaC-008 (IMPORTANT) — Provisioned concurrency never applied (`infrastructure/stacks/CostsCrunchStack.ts`)
- **Gap**: `provisionedConcurrency` prop was computed per stage and passed in, but no aliases or auto-scaling constructs were wired up; prod incurred cold starts despite the intent.
- Fix: when `useProvisionedConcurrency` is true, adds `fn.addAlias('live')` + `alias.addAutoScaling({ minCapacity: 1, maxCapacity: 10 }).scaleOnUtilization({ utilizationTarget: 0.5 })` for `expensesLambda`, `groupsLambda`, and `snsWebhookLambda`.

### IaC-009 (IMPORTANT) — DynamoDB billing always on-demand (`infrastructure/stacks/CostsCrunchStack.ts`)
- **Gap**: `capacityMode` prop was resolved from context but the `TableV2` `billing` field hardcoded `Billing.onDemand()`; provisioned billing was never activated for staging or prod.
- Fix: conditional billing — `Billing.provisioned({ readCapacity: Capacity.fixed(isProd ? 50 : 5), writeCapacity: Capacity.autoscaled({ maxCapacity: isProd ? 20 : 5 }) })` when `capacityMode === 'provisioned'`, else `Billing.onDemand()`.

### IaC-010 (IMPORTANT) — Redis cacheNodeType no-op ternary (`infrastructure/stacks/CostsCrunchStack.ts`)
- **Gap**: Both branches of `isProd ? "cache.t2.micro" : "cache.t2.micro"` were identical; prod never received the larger node type intended for production workloads.
- Fix: `cacheNodeType: isProd ? "cache.t4g.small" : "cache.t2.micro"`.

### IaC-011 (IMPORTANT) — WEBSOCKET_ENDPOINT missing from imagePreprocessLambda (`infrastructure/stacks/CostsCrunchStack.ts`)
- **Gap**: `WEBSOCKET_ENDPOINT` was only injected into `wsNotifierLambda`; `imagePreprocessLambda` read `process.env.WEBSOCKET_ENDPOINT || ""` and silently skipped quarantine push notifications when the value was empty (same root as DEP-003).
- Fix: `imagePreprocessLambda.addEnvironment("WEBSOCKET_ENDPOINT", wsEndpoint)` added after `wsStage` is created; both lambdas now share the same resolved endpoint value.

### IaC-013 (IMPORTANT) — wsHandlerLambda absent from monitoring (`infrastructure/stacks/CostsCrunchStack.ts`)
- **Gap**: `wsHandlerLambda` was not in the `lambdaMonitoring` array; WebSocket `$connect`/`$disconnect` failures produced no CloudWatch error-rate or duration alarms.
- Fix: added `{ fn: wsHandlerLambda, timeout: 29 }` to `lambdaMonitoring`.

### IaC-017 (IMPORTANT) — CfnOIDCProvider EntityAlreadyExists (`infrastructure/stacks/GitHubActionsStack.ts`)
- **Gap**: `new openIdConnect.CfnOIDCProvider(...)` fails with `EntityAlreadyExists` if the GitHub OIDC provider is already registered in the AWS account; every re-deploy of the GitHubActionsStack would fail at this resource.
- Fix: replaced with `OpenIdConnectProvider.fromOpenIdConnectProviderArn(this, 'GithubOidcProvider', \`arn:aws:iam::${this.account}:oidc-provider/token.actions.githubusercontent.com\`)` to import the existing provider idempotently. Updated the output value from `attrArn` → `openIdConnectProviderArn`.

### IaC-018 (IMPORTANT) — alarmsTopic has no subscriptions (`infrastructure/stacks/CostsCrunchStack.ts`)
- **Gap**: All Lambda error-rate, duration, DynamoDB throttle, Textract pipeline, and DLQ alarms published to `alarmsTopic` but no email or endpoint was subscribed; every alarm fired into a void.
- Fix: `alarmsTopic.addSubscription(new EmailSubscription(alarmEmail))` when `--context alarmEmail=<addr>` is passed to `cdk deploy` or `cdk synth`. The subscription is conditional so synth/deploy without the context key continues to work.
